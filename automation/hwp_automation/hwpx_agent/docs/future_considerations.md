# 추후 개발 고려사항

## 이 문서의 목적

이 문서는 "지금 당장 구현하지는 않았지만, 다음 단계에서 꼭 판단해야 할 것"을 정리한 문서입니다.

현재 1차 완료 범위는 `docs/phase1_completion.md`에 고정합니다. 이 문서는 그 다음 단계 판단만 다룹니다.

## 1. 지원 범위 확장

현재는 아래 범위가 검증됐습니다.

- 본문 텍스트 문단
- 안전한 텍스트 표 셀

다음에 확장할 후보는 아래입니다.

- 복합 컨트롤 문단
- 그림이 포함된 문단
- 각주, 미주
- 글상자 내부 텍스트
- 복잡한 표 셀
- 머리말, 꼬리말
- 마스터페이지

## 2. 자동 복원 안전장치 강화

지금도 `expected_current_text` 비교가 있지만, 더 강화할 수 있습니다.

- 공백 정규화 기준 통일
- origin 위치 재확인 로직 추가
- 충돌 시 자동 중단
- 한 문서에서 다수 수정 시 롤백 전략 정의

## 3. 교정 품질 고도화

현재는 구조 연결이 중심입니다.

다음 단계에서 검토할 수 있습니다.

- `kiwipiepy` 기반 맞춤법/띄어쓰기
- 규칙 사전 추가
- 표 전용 규칙
- 제목/목차 전용 규칙
- 숫자, 단위, 괄호 패턴 검사

## 4. 표 셀 처리 정책

현재는 모든 셀을 자산화합니다.

장점:

- 추적이 정확함
- 복원 연결이 쉬움

주의점:

- 셀 수가 매우 많아짐
- 교정 라인 수가 크게 증가함
- 리뷰 파일이 커질 수 있음

다음에 결정할 수 있는 방향은 아래 2가지입니다.

- 모든 셀 유지
- 검사용 셀만 별도 필터링

## 5. 성능과 대용량 문서 대응

목표 문서는 평균 200페이지 내외입니다.

고려할 점:

- 대형 문서에서 실행 시간
- 표 셀 수 증가에 따른 메모리 사용량
- run 폴더 크기 증가
- proofread 라인 수 증가

필요하면 다음 단계에서 아래를 검토할 수 있습니다.

- 스트리밍 처리
- 셀 필터링
- 이미지 추출 옵션화
- 로그 압축

## 6. API 형태 정리

현재는 CLI 중심입니다.

멀티에이전트 호출 환경에 맞추려면 아래를 더 정리해야 합니다.

- 입력 JSON 규격
- 출력 JSON 규격
- 단계별 표준 에러 형식
- 실행 성공/실패 상태 코드
- 비동기 실행 여부

즉, 나중에는 아래처럼 고정하는 것이 좋습니다.

- `parse`
- `proofread`
- `review_to_plan`
- `rebuild`

## 7. 테스트 자동화

현재는 실제 파일로 확인하는 흐름이 중심입니다.

다음에는 자동 테스트를 붙이는 것이 좋습니다.

- 페이지 수 검증
- 문단 수 검증
- 표 수 검증
- 표 셀 수 검증
- `origin_type=table_cell` 생성 검증
- rebuild 후 문자열 반영 검증
- rebuilt HWPX ZIP 유효성 검증

## 8. 사용자 문서 고도화

지금은 초보자용 문서가 있지만, 나중에는 아래로 나누는 것이 좋습니다.

- 실사용자용 문서
- 운영자용 문서
- 개발자용 문서
- 장애 대응 문서

## 9. 품질 기준 문서화

최종 운영 전에는 "어디까지 성공으로 볼지" 기준을 정해야 합니다.

예:

- 페이지 정합성 허용 오차
- 자동 수정 허용 범위
- 수동 확인 필수 영역
- rebuild 성공 판정 기준

이 기준이 있어야 테스트 결과를 일관되게 판단할 수 있습니다.

## 10. 지금 시점의 추천 우선순위

다음 단계 우선순위는 아래가 적절합니다.

1. 자동 테스트 정리
2. 지원 범위와 제외 범위 문서화
3. 멀티에이전트 호출용 입력/출력 규격 정리
4. 복합 컨트롤 영역 확장 여부 판단
